# 앱 개발 실행 명세 — 단일 파일 전달용

버전: 1.0 / 작성일: 2026-09-10

## 0. 이 문서를 받은 개발 에이전트에게

이 문서를 사용자가 만들려는 앱의 개발 기준으로 적용하라. 사용자가 별도로 제공한
앱 목적·요구사항과 함께, 설계부터 구현·검증·문서·배포 준비까지 수행하라.
계획이나 화면 시안만 제시하고 멈추지 말고 실제로 실행 가능한 결과물을 만들어라.

이 파일은 독립적으로 사용할 수 있다. 원 TMM 프로젝트, 이전 대화, 개인 폴더,
외부 템플릿, 특정 모델 버전에 접근할 필요가 없다. TMM의 개발 경험을 일반화한
실행 명세이며, 아래 수치·구조 중 기본값으로 표시한 항목은 새 프로젝트를 위한 제안이다.
이 문서 자체가 동일한 결과 품질이나 특정 모델의 성능을 보장하지는 않는다.

사용자의 최신 명시적 요구사항과 실행 환경의 상위 지침을 우선한다.
기존 프로젝트에서는 구현으로 현재 동작을 확인하고, 명세와 다른 부분을 기록한다.
구현에 버그가 있을 수 있으므로 현재 동작을 자동으로 정답으로 취급하지 않는다.

### 최소한 필요한 프로젝트 정보

사용자가 앱 목적을 한두 문장으로 제공했다면 합리적인 기본값으로 시작하라.
아래 항목을 모두 질문지로 보내지 말고 대화·기존 파일에서 먼저 파악하라.

```text
앱 목적: 누가 어떤 입력으로 어떤 작업을 하고 어떤 결과를 얻는가?
필수 작업: 반드시 가능한 작업 1~3개.
입력/출력: 파일 형식 또는 예시 데이터, 결과 화면과 저장 형식.
실행 환경: 로컬/웹, 대상 OS, 기존 프로젝트가 있는가?
특별한 제약: 필수 계산식, 장비, 비공개 데이터, 지정 기술, 배포 요구사항.
```

앱 목적 자체가 없으면 그것부터 짧게 질문하라. 핵심 계산식·실제 장비 프로토콜처럼
추측하면 결과가 달라지는 정보는 확인하되, 그 정보와 독립적인 구조·UI 작업은 진행하라.
샘플 데이터가 없으면 합성 예제를 만들 수 있지만 예제라고 표시하고 실제 데이터로 가장하지 마라.

## 1. 기본 제품 방향과 범위

별도 지시가 없는 연구·분석·데이터 도구는 로컬에서 실행하는 작업 앱으로 설계한다.
핵심 작업은 설치된 의존성과 로컬 데이터만으로 실행 가능하게 한다.
클라우드, 로그인, 결제, 팀 권한, 자동 설치 업데이트는 요구될 때 범위에 추가한다.

첫 화면에는 입력·작업 실행·결과 확인을 배치한다. 앱 소개보다 사용자의 핵심 작업을
앞에 둔다. 기본 사용자 흐름은 다음과 같다.

```text
입력 선택/불러오기 → 조건 설정 → 실행 → 결과 확인/탐색 → 저장/내보내기 → 재실행
```

완료 수준은 구분해서 보고한다.

- 구현 완료: 필요한 코드가 연결되어 실제 입력으로 결과를 만든다.
- 검증 완료: 해당 환경에서 실행·주요 흐름·정확성 검사를 실제 수행했다.
- 배포 준비 완료: 요청된 배포 방식에 맞는 패키지와 안내를 준비했다.
- 배포 완료: 요청된 대상에 실제 전달·게시했고 접근 또는 실행을 확인했다.

새 앱의 기본 범위는 로컬 실행, 주요 작업 검증, 내보내기, 사용자 데이터 보호,
문서와 재현 가능한 실행 방법까지다. 협업자 배포가 요청되면 패키지 검증을 추가한다.
기존 앱의 작은 수정에는 영향받는 항목만 적용하고 전체 앱 재개발로 확대하지 마라.

## 2. 작업 진행 순서

1. **확인:** 기존 파일·실행 방법·사용자 변경·프로젝트 지침을 읽는다.
2. **범위 고정:** 필수 작업, 입력/출력, 기본값, 미확정 사항, 완료 검사를 기록한다.
3. **최소 흐름 연결:** 실제 입력 하나가 핵심 로직을 거쳐 결과·내보내기까지 이어지게 한다.
4. **핵심 확장:** 나머지 필수 작업, 오류 처리, 상태 저장, 긴 작업 제어를 구현한다.
5. **사용 품질 개선:** 배치·좌표·키보드·반응형·성능을 실제 화면에서 확인하고 수정한다.
6. **검증:** 계산·데이터 계약 테스트와 실제 사용자 흐름 검사를 수행한다.
7. **인수인계:** 실행·저장 위치·한계·검증 결과·배포 방법을 최신 상태로 남긴다.

가역적인 로컬 구현·수정은 매 단계 승인을 재요청하지 말고 진행하라.
사용자가 이미 허용한 범위는 이어서 수행하라. 게시, 외부 전달, 데이터 삭제 등은
해당 작업이 요청 범위에 포함되는지 판단하고 필요한 경우에만 구체적인 결과를 준비한 뒤 확인하라.
사용자 요청 없는 메시지 발송이나 사용자 데이터 영구 변경을 개발 과정에 끼워 넣지 마라.

중간 요청은 기본적으로 진행 중인 작업의 보완으로 반영한다.
변경 요청 때문에 원래 필수 기능이 조용히 빠지지 않게 요구사항 기록을 갱신하라.
진행 보고는 발견한 사실, 해결한 문제, 다음 확인 대상을 짧게 전달하라.

## 3. 기술 선택과 구조

기존 코드가 있다면 현재 구조를 우선 활용한다. 새 기술 도입은 구체적인 필요가 있을 때 한다.
새 로컬 과학 계산 앱의 기본 후보는 Python 계산층과 HTML/CSS/JavaScript 브라우저 UI다.
프레임워크·패키지는 현재 환경과 요구사항에 맞게 선택하고 선택 이유를 짧게 남긴다.
설치가 필요한 의존성은 프로젝트 설정 파일에 선언한다.

책임 경계는 다음과 같이 유지한다. 각 책임이 반드시 별도 서비스일 필요는 없다.

| 계층 | 책임 | 지켜야 할 경계 |
| --- | --- | --- |
| UI | 입력, 탐색, 상태 표시, 그래프 조작 | 핵심 계산식을 이벤트 처리기에 넣지 않는다 |
| 애플리케이션 | 입력 검증, 작업 실행, 결과 수명, 파일 처리 | UI와 계산 사이의 계약을 명시한다 |
| 핵심 로직 | 계산, 변환, 분석, 도메인 규칙 | UI 없이 직접 호출하고 검증할 수 있다 |
| 저장·내보내기 | 설정, 사용자 자료, 결과, 메타데이터 | 원본과 표시 결과를 구분한다 |
| 실행·배포 | 경로, 시작/종료, 패키지, 로그 | 특정 개발자의 경로에 의존하지 않는다 |

권장 구조는 아래와 같다. 언어나 기존 저장소에 맞춰 이름을 바꿀 수 있다.

```text
project/
  web/ 또는 app/         UI
  backend/               작업·파일·상태 조정
  src/                   재사용 가능한 핵심 로직
  tests/                 의미 있는 검증과 회귀 테스트
  examples/              작은 재현 예제
  docs/                  계약·계산·검증 설명
  scripts/               실행·빌드 유틸리티
  README.md
  AGENTS.md
  DEVELOPER_HANDOFF.md
  CHANGELOG.md
  프로젝트 의존성 설정
  .gitignore
```

단위 변환, 상수, 데이터 형식, 좌표 변환을 중앙화하라.
분석 기능은 가능한 한 명시적 입력을 받고 결과를 반환하게 만들어라.
거대한 단일 파일이 서로 무관한 책임을 갖게 되면 책임 기준으로 나누되,
한 번 쓰는 기능을 위해 불필요한 계층이나 플러그인 시스템을 만들지 마라.

## 4. UI의 구체적인 기본값

기본 취향은 단정한 Apple 계열 로컬 도구 느낌, 밝은 배경, 은은한 패널,
절제된 테두리·그림자, 파란 강조색, 촘촘하지만 읽기 쉬운 배치다.
아래는 시작값이며 사용자 요구와 데이터 가독성에 맞게 조정한다.

```css
:root {
  --bg: #f5f6f8;
  --surface: #ffffff;
  --text: #1d1d1f;
  --muted: #5f636b;
  --border: #d9dde3;
  --accent: #0969da;
  --danger: #b42318;
  --radius: 10px;
}
```

- 기본 본문 14px 전후, 컨트롤 높이 32~36px 전후로 시작하되 읽기·조작성을 확인한다.
- 왼쪽 설정 영역은 280~320px 정도를 출발점으로 삼고 결과 영역에 남은 폭을 준다.
- 오른쪽 상세 패널은 필요할 때만 둔다. 작은 화면에서는 접거나 아래로 이동한다.
- 간격은 4/8/12/16/24px 등의 일정한 척도로 정렬한다.
- 색은 역할 토큰으로 관리하고 오류·선택·포커스는 색 외의 단서도 제공한다.
- 여러 테마는 사용자 요구가 있을 때 추가한다. 테마 수가 완료 기준은 아니다.

입력에는 이름·값·단위를 구분해서 표시한다. 숫자는 직접 입력할 수 있게 하고
범위·유한값·필수 여부를 검증한다. 고정 선택지는 자유 입력 대신 적절한 선택 컨트롤을 쓴다.
백엔드가 있는 앱은 입력 검증을 UI에만 맡기지 않는다.

주 실행 버튼은 분명하게 하나의 작업을 나타내게 한다. 실행 중 버튼과 내보내기 위치가
움직이지 않도록 상태 표시 공간을 확보한다. 긴 설명은 Guide에 두고 현재 판단에 필요한
경고·단위·상태는 해당 컨트롤이나 결과 근처에 둔다.

키보드 포커스를 표시하고, 입력 레이블을 연결하고, 대화상자 닫기와 포커스 복귀를 확인한다.
데스크톱·노트북 폭에서 실제 화면을 확인한다. 시작 검사 폭은 1440px와 1024px를 사용할 수
있으며 모바일이 범위에 있으면 약 390px도 확인한다. 가로 넘침, 겹침, 버튼 잘림을 수정한다.

## 5. 상태와 긴 작업

입력 편집 상태, 실행에 사용한 입력, 계산 결과, 화면 표시 설정을 분리하라.
결과에는 실행 당시 입력 스냅샷을 연결하고 이후 입력 편집으로 그 기록을 바꾸지 마라.

다음 상태를 다룬다.

| 상태 | 사용자에게 보여줄 내용 | 필요한 동작 |
| --- | --- | --- |
| 초기/비어 있음 | 시작 방법과 필요한 입력 | 작은 예제 또는 입력 경로 제공 |
| 입력 오류 | 문제 있는 필드와 수정 방법 | 잘못된 실행 차단 |
| 실행 중 | 실제 진행 상태 | 중복 실행 제어, 필요시 중단 |
| 성공 | 결과와 적용된 조건 | 탐색·내보내기 활성화 |
| 입력 변경됨 | 표시 결과가 이전 조건임을 표시 | 재실행 가능 |
| 중단됨 | 중단 사실과 결과 보존 여부 | 다시 실행 가능 |
| 실패 | 원인 요약과 복구 방법 | 입력 보존, 재시도 가능 |

오래 걸리는 계산은 키 입력마다 실행하지 않는다. 가벼운 색상·범위·표시 변경은
캐시된 결과로 처리한다. 이전 작업의 늦은 응답이 최신 결과를 덮어쓰지 않게 작업 식별자를 확인한다.
중단은 안전한 체크포인트에서 반영하고, 부분 결과가 있으면 완료 결과와 구분한다.
계산 비용과 메모리를 고려해 그리드·파일 크기·캐시 수명에 합리적인 한도를 둔다.
측정하지 않은 처리시간이나 정확한 진행률을 꾸며내지 마라.

## 6. 데이터·좌표·내보내기 계약

데이터 형식은 최소한 다음 의미를 정의한다.

- 입력: 필수 항목, 자료형, 허용 범위, 단위, 기본값, 누락/잘못된 값 처리.
- 배열: 축 이름·순서, 모양, 원점, 정렬 방향, 복소수/결측값 표현.
- 결과: 원본/가공 여부, 실행 조건, 적용된 변환, 결과 식별자 또는 생성 정보.
- 저장: 형식 버전, 기존 데이터 읽기 정책, 저장 위치.
- 오류: 사용자가 수정할 입력 오류와 실행 실패의 구분.

그래프가 있는 앱은 데이터 인덱스 ↔ 물리 좌표 ↔ 표시 좌표 사이의 변환을 명시한다.
CSS 크기와 캔버스 내부 픽셀 크기를 혼동하지 마라. 축 반전, 확대, 화면 크기 변경,
비정사각형 배열에서도 이미지·hover·마커·추출 값·내보내기가 일치해야 한다.
보간된 표시가 원본 샘플과 다르면 그 차이를 처리하고 필요하면 안내한다.

기본 그래프 기능은 축 이름·단위·읽기 쉬운 눈금, 필요한 hover, 확대와 초기화,
현재 화면 이미지 저장, 원래 수치 데이터 내보내기다. 작업에 맞지 않는 기능은 생략 사유를 남긴다.

내보내기는 앱 밖에서도 해석할 수 있어야 한다.

- PNG 등 이미지에는 필요한 축·단위·범례를 포함한다.
- CSV 등 수치 파일에는 열 이름과 축을 명확히 기록한다.
- 다차원 데이터는 행/열 또는 펼침 순서를 명시한다.
- 재현에 필요한 입력 조건, 앱 버전, 단위, 처리 방법을 함께 저장한다.
- 화면에 보이는 일부 범위와 전체 데이터 중 무엇을 내보내는지 명확하게 한다.
- 내보낸 파일을 실제로 열거나 다시 읽어 값·축·메타데이터를 확인한다.

## 7. 사용자 자료와 설정 보호

읽기 전용 앱 자원과 사용자가 수정하는 자료를 구분한다.
설치형 로컬 앱은 사용자 자료를 실행 파일 밖의 OS별 사용자 데이터 위치에 둔다.
설정·테마·분석 자료는 목적별로 구분해서 하나를 초기화해도 다른 항목이 손상되지 않게 한다.

사용자가 요청한 저장·편집은 수행하되 개발이나 검증을 위해 실제 사용자 자료를
임의로 변경하지 마라. 테스트는 임시 경로와 복사본·합성 데이터를 사용한다.
중요한 저장은 쓰기 실패로 기존 파일이 망가지지 않게 임시 파일 후 교체 등의 방식을 고려한다.
형식 변경은 버전과 이전 절차를 정의하고 기존 파일로 확인한다.

사용자가 만든 데이터, 출력, 로그, 가상환경, 비밀값, 기기별 설정과 생성된 배포 파일은
소스 코드와 구분해 관리한다. 배포 패키지에 포함할 자원을 명시적으로 선택한다.
외부 계정·네트워크 기능은 앱 목적에 필요한 범위에서만 추가한다.

## 8. 연구·분석 기능의 추가 요구사항

계산이나 데이터 분석이 있는 경우 적용한다. 일반 업무 앱에 물리학 검사를 억지로 추가하지 않는다.

- 식 또는 알고리즘, 변수 의미, 단위, 부호·축 규약, 근사, 적용 범위를 기록한다.
- 측정값, 가공값, 피팅값, 모델 추정값을 구분한다.
- 입력 자료의 출처, 원래 단위, 성분 매핑, 정리·보간 등 처리 이력을 남긴다.
- 알려진 정답, 극한, 보존 관계, 대칭성 등 독립적인 기준으로 검증한다.
- 해상도·샘플 수·수치 허용오차 변화에 대한 수렴을 필요한 범위에서 확인한다.
- 복잡한 해석 전에 더 단순한 대안 설명과 대조 조건을 확인한다.
- 수치 결과를 얻었다는 사실과 해당 현상을 입증했다는 결론을 구분한다.
- 검증이 부족한 모델은 미검증 범위를 표시하고 확정적 해석을 피한다.

예를 들어 광학 앱의 밝은 반사 응답만으로 특정 모드나 강결합을 확정할 수 없다.
이 원칙은 다른 분야에서도 시각적 패턴을 도메인 결론으로 단정하지 않는 기준으로 적용한다.

## 9. 검증과 완료 판정

초기에 요구사항별 확인 방법을 정하고 구현 후 증거를 채운다.
단순 파일 존재 검사나 문법 검사만으로 사용자 기능 검증을 대체하지 마라.

| 항목 | 최소 확인 | 합격 기준 |
| --- | --- | --- |
| 실행 | 문서의 시작 명령으로 앱 실행 | 작업 화면이 열리고 필요한 서비스가 응답 |
| 주요 작업 | 작은 실제/합성 입력으로 끝까지 실행 | 입력 → 결과 → 내보내기가 연결 |
| 잘못된 입력 | 누락·범위 밖·잘못된 형식 입력 | 이해 가능한 오류, 기존 상태 보존 |
| 계산·분석 | 독립 기준 또는 대표 회귀 예제 | 명시한 허용오차·기대 동작 충족 |
| 좌표 | 모서리·중앙·직사각형·확대 후 확인 | 표시와 선택 값·수치 파일 일치 |
| 상태 | 실행·실패·재시도·입력 변경 | 잘못된 최신 상태 표시나 결과 덮어쓰기 없음 |
| 저장 | 저장 후 새로고침/재실행 | 약속한 설정과 자료가 복원 |
| 내보내기 | 파일 다시 열기/읽기 | 값·단위·축·범위·조건이 일치 |
| 화면 | 대상 화면 폭에서 실제 확인 | 넘침·겹침·접근 불가 핵심 버튼 없음 |
| 배포 | 요청된 OS의 패키지 실행 | 개발 소스 없이 실행하고 사용자 자료 보존 |

적용되지 않는 행은 이유를 기록한다. 버그 수정에는 오류를 잡는 회귀 검사를 우선한다.
UI 전용의 작고 가역적인 변경은 직접 확인으로 충분할 수 있다.
자동 테스트, 문법 검사, 브라우저 확인, 패키지 확인은 각각 수행 여부를 구분한다.
사용할 수 없는 OS·브라우저·외부 장비는 미검증이라고 기록하고 통과했다고 보고하지 마라.
같은 검사를 이유 없이 반복하기보다 실패·변경·남은 위험에 맞춰 추가 검증한다.

## 10. 실행·배포 요구사항

실행 명령, 의존성 설치, 종료 방법, 오류 로그 위치를 문서화한다.
로컬 서버는 기본적으로 loopback에서 실행하고 포트 충돌 시 대체 포트 또는 명확한
복구 안내를 제공한다. 소스 실행용 스크립트와 배포용 설치·실행 파일을 구분한다.

배포가 요청되었다면 먼저 대상 OS/아키텍처와 소스 공개 범위를 정한다.
타깃 OS에서 빌드·실행을 확인하고, 기존 사용자 데이터가 패키지 교체 후 유지되는지 검사한다.
자동 다운로드·설치는 별도 요청이 없으면 기본 기능에 포함하지 않는다.
업데이트 확인 기능을 추가한다면 연결 실패가 핵심 로컬 작업을 막지 않게 한다.
비공개 소스 배포가 조건이면 공개 산출물의 포함 파일을 검사하고 바이너리화 자체를
완전한 소스 비밀 보장으로 설명하지 마라.

릴리스에는 버전이 맞는 패키지·변경 이력·실행 안내를 포함한다.
생성된 ZIP·빌드 폴더는 기본적으로 git에서 제외한다.
빌드 성공, 다른 기기 실행 확인, 외부 게시 성공을 구분해서 보고한다.

## 11. 다음 개발자가 이어갈 수 있는 산출물

필요한 문서를 작업 규모에 맞춰 작성한다. 작은 프로젝트는 일부 문서를 합칠 수 있지만
아래 정보는 빠뜨리지 마라. 아직 없는 파일을 읽으라고 요구하는 인수인계는 만들지 마라.

- **README:** 목적, 빠른 시작, 의존성, 지원 환경, 예제, 저장 위치, 내보내기, 문제 해결.
- **USER_MANUAL 또는 Guide:** 주요 사용자 흐름, 입력 의미, 결과 해석, 복구 방법.
- **DEVELOPER_HANDOFF:** 현재 구조, 책임별 파일, 계약, 수정 시 주의사항, 실행·검증 명령,
  실제 검증 범위, 남은 문제와 다음 단계.
- **CHANGELOG:** 실질적 변경의 날짜·내용·호환성 또는 과학적 영향.
- **AGENTS:** 이 명세를 읽는 순서, 프로젝트의 핵심 불변 조건, 데이터 보호, 검증 명령을 짧게 기록.
- **요구사항 검증표:** 필수 요구, 구현 위치, 확인 방법, 결과, 미완료 이유.

새 프로젝트에 이 명세 파일을 함께 보관하고 `AGENTS.md`에서 참조할 수 있다.
기존 지침은 덮어쓰지 말고 사용자 요구와 충돌하지 않도록 통합한다.
문서는 미래 계획과 현재 구현을 구분하고, 현재 구현이 바뀌면 관련 설명도 수정한다.
개인 절대 경로·예전 대화·존재하지 않는 외부 파일이 다음 개발자의 필수 의존성이 되지 않게 한다.

## 12. 최종 전달 형식

최종 응답은 다음 정보가 스스로 이해될 정도로 간결하게 작성하라.

```text
완성한 것: 사용자가 할 수 있게 된 핵심 작업.
실행 방법: 실제 확인한 명령 또는 실행 파일.
산출물: 코드/앱/문서/패키지의 경로 또는 링크.
검증: 실제 수행한 주요 검사와 결과.
남은 한계: 미완료·미검증 범위와 필요한 외부 조건. 없으면 생략.
```

장식적인 화면이나 성공 메시지만으로 완료하지 마라.
핵심 입력 → 처리 → 결과 → 내보내기 흐름, 데이터 보존, 검증 증거,
다음 개발자가 재실행할 수 있는 설명을 기준으로 완료를 판단하라.
